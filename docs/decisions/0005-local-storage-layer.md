# 0005 — The `~/.etchable/` storage layer (and de-sqliting zen eval)

Status: accepted, 2026-08-08. Amends 0004 (the offline-retry-on-declared-
dependencies path is gone: remote `[dependencies]` are now unsupported
outright).

## Decision

Everything the app persists outside a project lives under one predictable,
deletable directory:

```
~/.etchable/                  ETCHABLE_HOME override
  cache/                      disposable, safe to rm -rf; ETCHABLE_CACHE_DIR override
    lcsc/v1/…                 moved from ~/Library/Caches/etchable
  state/
    etchable.sqlite3          sea-orm/sqlite: recents, agent sessions, prefs
  runtime/
    mcp-config-{pid}.json     per-instance scratch, swept at startup
```

`crates/store` is the single authority: `paths` (the layout + legacy cache
adoption) and an async `Store` on **sea-orm 2.0** with embedded
**sea-orm-migration** Rust migrations run at open. A deliberate XDG
deviation (`.cargo`/`.claude` tradition): one dir to document, one dir to
delete, identical on every platform, and the crate stays tauri-free.

## Getting sea-orm required de-sqliting zen eval

Cargo allows exactly ONE crate in a build graph to link the native
`sqlite3` library. That slot was occupied by `libsqlite3-sys 0.38` via the
pinned `pcb-zen` → `rusqlite 0.40`, and every published `sqlx-sqlite`
(sea-orm's only backend) caps below 0.38 — sea-orm was a hard build error.

`pcb-zen` needed sqlite for exactly one thing: `cache_index.rs`, the index
of REMOTE package resolution (git-fetched Zener packages). Everything
zen-build actually consumes — the eval engine, `ResolutionResult`, the
frozen-resolution types, stdlib materialization primitives — lives in
sqlite-free `pcb-zen-core`, and zen-build called only two `pcb_zen`
functions. So:

- `crates/zen-build/src/frozen.rs` reimplements resolution for etchable's
  world on public core APIs (~150 lines): workspace packages + the stdlib,
  faithful to upstream's `package_resolver/resolve.rs` for everything kept.
  A manifest declaring `[dependencies]` fails with a clear
  "remote packages are not supported in etchable" error — accepted cost,
  decided explicitly: etchable projects are self-contained by design
  (0004), and only foreign diodeinc/pcb-style repos are affected.
- Stdlib materialization no longer routes through upstream's sqlite module:
  `pipeline::materialize_stdlib` covers both the bundled source (packaged
  app) and exe-ancestor discovery (dev), injecting the same `[patch]
  stdlib` entry either way. A project-authored stdlib patch wins outright.
- The `pcb-zen` dependency is deleted. The hard-rule pin list narrows to
  `pcb-zen-core` / `pcb-sch` / `pcb-eda` / `pcb-component-gen` + the
  starlark fork.

Result: one `libsqlite3-sys` in the binary (sqlx's bundled copy), owned by
our own state store.

## The state db

sea-orm entities `projects` / `agent_sessions` / `prefs`; timestamps are
unix milliseconds (`Date.now()`-compatible); single-connection pool
(desktop app, trivial pragma semantics; sqlx's sqlite defaults give WAL +
5 s busy timeout). Growth is bounded in the write path (50 projects, 100
sessions per workspace).

- **Recents**: recorded in `open_board_file` for real projects only
  (bare-`.zen` opens are the dev path and would pollute the list), before
  the build — a broken build is still a project the user wants back.
- **Agent sessions**: recorded in `agent::pump_events` (the only place the
  session id verifiably exists) — `init` upserts, `result` bumps
  `last_used_at`. `send_message`/`resume_session` park the title /
  resumed-from in pending slots the init recording consumes.
  `claude --resume` forks a NEW session id; `resumed_from` links the chain
  and listings hide superseded ancestors.
- **Prefs**: JSON values, frontend-owned, backend never interprets
  (`ui.panelWidth`, `ui.activeTab`).

**Never-brick policy:** a failed open — including a db touched by a newer
build, which the migrator refuses because its `seaql_migrations` rows
wouldn't match the embedded set — logs once and the app runs without
persistence. No auto-wipe.

## Type flow: ts-rs (pilot)

Store DTOs (`RecentProject`, `SessionSummary`) derive `ts_rs::TS`;
`pnpm gen:store-types` regenerates `apps/desktop/src/generated/` (CI runs
`--check`, mirroring gen:symbol-geom). `types.ts` re-exports them so the
frontend keeps one import path. The rusqlite→sea-orm rewrite changed zero
generated bytes — the DTO seam is the contract. Migrating the hand-written
mirrors (BuildView, agent events) to codegen is a possible follow-up
(tauri-specta), not this change.

## Rejected

- rusqlite + rusqlite_migration for the store: worked (first
  implementation), but the user wants sea-orm's migration/entity layer, and
  de-sqliting zen eval made it possible.
- `tauri-plugin-sql` + drizzle in the webview: state's writers are the
  Rust backend (MCP server, builder, agent host); the webview is a view.
- tauri `app_data_dir`: couples the layout to tauri + the bundle
  identifier; `crates/store` stays a leaf.
- Auto-wiping a newer-build db: recents/prefs are low-value, but silently
  destroying another build's state is how trust dies.
